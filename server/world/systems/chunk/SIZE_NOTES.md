# ChunkUpdating 文件规模说明

## 当前原因

`updating.rs` 是上游既有的区块更新主流程，当前 927 行。它按固定顺序完成活动方块、待处理方块、方块实体、光照传播、保存、重建网格和 UPDATE 广播；这些步骤共享同一个 `Chunks` 可变借用与同一批更新结果。本轮只在末端接入 `ChunkProjection`，将权威更新投影后按区块兴趣定向发送，没有向文件加入玩法状态或矿石生成规则。

本轮不做机械拆分，因为移动光照或方块实体阶段会同时改变调度顺序、借用边界和广播时机，超出反透视投影的变更范围。

## 约束

- `Chunks` 始终保存权威体素；`ChunkProjection` 只能生成客户端视图，不能回写权威区块。
- identity 投影必须保持原有单条 `ClientFilter::All` 广播路径和 legacy 行为。
- 非 identity 投影只能向对目标区块有兴趣的客户端发送定向 UPDATE，不能跨 World 或跨区块泄露。
- 光照、保存和网格重建必须先基于权威更新完成，再生成客户端投影。

## 后续计划

- 下次修改活动方块或光照算法时，优先把 `process_pending_updates` 的方块实体、光照和网格阶段拆成同目录专责模块。
- 拆分前补齐顺序等价、跨区块光照、方块实体联动和 legacy 广播回归；拆分后由 `updating.rs` 仅保留系统数据解构与阶段编排。
- 在这些门禁齐备前，不为满足行数做大规模搬移，避免把公平性修复与上游区块算法重构混在同一提交。
